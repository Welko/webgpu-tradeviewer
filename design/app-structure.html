What lives in Viewer::App

How it's built today, how its parts depend on each other, and ways to make it smaller. The telemetry design is the one we have now: App owns it.

1. The parts and how they talk

App has nine parts. Each input changes one of them, and then a chain works out everything that depends on it, in a fixed order: the view's trades and price range, then the axes, then the summaries, then what the cursor picks. Most of the results land in one struct, mSettings, which is also exactly what the engine takes.

Blue: the chain every change runs through. Purple: the shared settings struct. Green: the GPU. Orange, dashed: telemetry and profiling, hooked into the rest.

2. Every input runs part of the same chain, by hand

Each public setter changes its piece of state, then calls the chain from the step it affects onwards. The order never changes, but it's written out again in each method, so it's easy to forget a step when adding one.

4. Ways to simplify it

In order of value for the effort. The first three keep the same shape (one App, telemetry inside it) and remove repetition. The fourth splits it up.

A. One refresh(from) instead of the chain spelled out in every setter recommended

Each setter changes its state, then says where the chain starts:

enum class Stage { View, Axes, Summaries, Pick, Sync };

void App::refresh(Stage from)
{
    // Each step uses what the ones before it found.
    switch (from) {
    case Stage::View:      findViewTrades();   [[fallthrough]];
    case Stage::Axes:      updateAxes();       [[fallthrough]];
    case Stage::Summaries: updateSummaries();  [[fallthrough]];
    case Stage::Pick:      updatePick();       [[fallthrough]];
    case Stage::Sync:      syncSettings();
    }
}

void App::resize(std::uint32_t widthPx, std::uint32_t heightPx)
{
    ...
    refresh(Stage::Axes);
}

The order lives in one place; adding a step can't miss a setter. Small, nothing changes from outside. Later, the same function could run once per frame from update() instead, which would give "one zoom per frame from wheel events" from the unscheduled list. But then getters like getAxes() would be stale until the next update(), and the tests read them straight after zooming, so I'd leave that for later.

B. One way to change the view: setView(range, why) recommended

zoomAt, panBy, resetView, showDay and setTrades each work out a time range, then call one private method with the reason:

enum class ViewChange { NewTrades, Reset, WholeDay, Zoom, Pan };

void App::setView(Core::TimeRange time, ViewChange why)
{
    mSettings.view.time = time;
    refresh(Stage::View);
    if (why != ViewChange::NewTrades) {
        mTelemetry.noteViewChange(time.getLengthUs(), why == ViewChange::Reset, why == ViewChange::WholeDay);
    }
}

Removes showNoon and noteViewChange, and the four separate telemetry calls become one. Telemetry stays in App and still knows nothing about it. The zoom limits and the noon/day ranges could become small functions next to Core::TimeRange, where they can be tested without a GPU.

C. Expose the GPU session and telemetry rather than forwarding to them recommended

GpuSession& getGpu() and Telemetry& getTelemetry() replace the nine orange methods: callers write app.getGpu().getHealth() or app.getTelemetry().flush().

GpuSession already has getHealth, getInfo and setWakeCallback. readPixels, needsRender and processEvents would move into it, with their "no engine while restarting" checks. That's where those checks belong anyway, since the session is what knows about restarts. noteDataLoaded goes the same way, with WebMain passing the trade count and span. App keeps setTelemetry and setProfiling, because those two must be decided together (the 1-in-30 GPU sample).

D. Split the pure parts into their own classes later, if still big

Three parts use no GPU and could each be a small class in Core, tested without a GPU:

  • View navigation: the time range, zoom limits, pan, noon and day, the price range fitted to the trades.
  • Summaries: allowed, threshold, the columns, and turning them into what the engine takes (getEngineColumns).
  • Picking: cursor plus pick rule, giving a highlight and the picked trade or column with its position.

App would then just coordinate: its parts, the refresh chain and the GPU. It's the biggest change, with more files and more types, and A–C may make it unnecessary. I'd decide after doing them.

E. Small tidy-ups optional

  • The time maths in getPickedColumn (a column's start and end) belongs with the column summaries in Core::Data.
  • getEngineColumns copies each summary into the engine's own type field by field. If the engine took Core::Data::ColumnSummary directly, the copy and its 17 lines would go. But the engine's type may be kept separate on purpose, to match the GPU buffer layout, so check that first.
  • generateSyntheticDay and the brief's date have nothing to do with App; they could move next to Core::Data::generateSyntheticTrades.

5. My suggestion

Do A, B and C together as one cleanup step. They leave the code that uses App almost unchanged (C changes call sites in WebMain, NativeMain and the tests), and remove roughly 100–150 lines, about a dozen public methods and all the scattered telemetry calls except the pick. Then look at App again before deciding on D.
