# Trade Viewer

A C++ WebGPU viewer for Binance BTC/USDT market data. It builds to WebAssembly with Emscripten and is hosted in a React page. It also runs natively.

Status: scaffold only. The viewer creates a WebGPU device and clears the surface each frame.

## Layout

```
cpp/
  modules/Core       no WebGPU dependency:
                       Core/Log.hpp     logging
                       Core/Range.hpp   time, value and index ranges
                       Core/Data/       trades, their CSV parser (Tardis and Binance), exact totals,
                                        the price tree, column summaries, synthetic trades
                       Core/Plot/       where trades go on screen, without a GPU: axis ticks and
                                        their labels, picking
  modules/Gpu        WebGPU rendering and compute. Public API is Gpu::Market::Engine (a
                     facade with no WebGPU types) and Gpu::Market::Style (marker sizes,
                     summary bars and the legend, no GPU needed). Context (device, surface...) and the
                     passes are internal (src/include): Gpu::Plot (plot area, grid) is
                     generic, Gpu::Market (trades) is about markets. Design: design/gpu.md
  apps/ViewerApp     the viewer:
                       App.cpp          ViewerAppLib: the platform-independent part
                                        (view state, input, engine), shared with BenchmarkApp
                       Scene.cpp        the image tests' scenes, drawn alike on every platform
                       NativeMain.cpp   GLFW window and loop
                       WebMain.cpp      embind `Viewer` class, loop driven by JS
  apps/TradeStatsApp native command line: a time range's trade count and amount, as the viewer computes them
  apps/BenchmarkApp  native command line: frame times at four zoom levels (and the whole day
                     drawing every trade), from the profiler
tools/check_ranges.py  checks TradeStatsApp against an independent calculation
tools/render-native.sh, compare-renderings.mjs (with package.json: pngjs), reference-renderings/,
                     check-benchmark.mjs and benchmark-baseline.csv (see Memory and speed between commits)
                     draw the image tests' scenes natively, and compare every platform's
                     renderings (see Image tests)
web/                 Vite + React + TypeScript
  src/viewer/        createViewer(), <ViewerCanvas>, its <ViewControls> toolbar and <Legend>, and
                     the tooltip of the trade or bar under the pointer
  src/data/          <DataPanel>, and loading files and the Binance sample
  scene.html, src/scene.ts  the image tests' scenes, one per page (scene.html?scene=hour)
  src/wasm/          generated by the Emscripten build (gitignored)
```

The platform side owns the frame loop: `requestAnimationFrame` on the web, a GLFW loop natively. Each frame it calls `update(nowMs)` (CPU state) and then `render()` (draw only). WebGPU init uses plain callbacks, so the same code runs on both platforms without Asyncify.

## Requirements

- CMake ≥ 3.24 and a C++23 compiler (tested with GCC 13)
- Node 18+
- [emsdk](https://emscripten.org/docs/getting_started/downloads.html) (tested with Emscripten 6.0.13)
- Native, Linux only for now: `sudo apt install libwayland-dev libxkbcommon-dev libx11-dev libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev zlib1g-dev`
- A browser with WebGPU
- Optional: [naga](https://crates.io/crates/naga-cli), to check shaders while building: `cargo install naga-cli --version 29.0.4`

The first configure downloads WebGPU-distribution (wgpu-native or emdawnwebgpu) and GLFW.

### Shaders

WGSL shaders live next to the pass that uses them, such as `cpp/modules/Gpu/src/Market/TradesPass.wgsl`. `gpu_embed_shader()` (`cpp/cmake/shaders.cmake`) turns each into a generated header, `Gpu/Shaders/<Name>.hpp`, holding it as a `std::string_view`, so binaries need no shader files at runtime. When naga is installed, every build checks each shader with it. Naga 29 is the compiler inside wgpu-native v29, so it catches what the native build would. CI requires it (`-DTRADEVIEWER_REQUIRE_NAGA=ON`). Chrome compiles with a different compiler, Tint, so the browser tests remain the web's check.

In VS Code or Cursor, the recommended [wgsl-analyzer](https://github.com/wgsl-analyzer/wgsl-analyzer) extension shows errors as you type, with hover and go-to-definition.

## Web

```bash
source ~/emsdk/emsdk_env.sh
cd web
npm install
npm run dev        # builds the wasm, then starts Vite on http://localhost:5173
```

`npm run build:wasm:dev` rebuilds only the C++ part. Vite reloads when `src/wasm/` changes.

`npm run build` creates the production site in `docs/`, which is gitignored. Use `npm run preview` to serve it.

**Function names:** development builds keep the C++ function names in the wasm (CMake option `TRADEVIEWER_WASM_NAMES`), so profilers and error stack traces show them. In Chrome, open DevTools, go to Performance, and record. Optimizations are the same either way, so the profile matches the published site. The published site leaves the names out; they would add about 17 KB gzipped. Each script sets the option explicitly, because CMake would otherwise keep the last value in its cache: `npm run dev` and `npm run build:wasm:dev` turn it on, and `npm run build` and `npm run build:wasm` turn it off.

## CI, GitHub Pages and releases

Work happens on `dev`; `main` gets what's ready to publish. `.github/workflows/ci.yml` runs on every push to either (and manually from the Actions tab):

1. **Native:** builds with the `native` preset and runs the tests with `ctest`, then again with profiling compiled out. It draws the image tests' scenes through a window (on Xvfb) and opens a real day's file. It then builds and tests the `native-release` preset, a single binary with wgpu-native linked in statically, and packages it with the licenses of what's linked in. Along the way it checks the visible counts (see [Viewing trades](#viewing-trades)) and runs `BenchmarkApp` on Mesa's lavapipe; both tables appear on the run's page, signed in to GitHub, and the benchmark is also kept as the `benchmark` artifact. The benchmark's memory and times are checked against the baseline (see [Memory and speed between commits](#memory-and-speed-between-commits)): a change in memory, or a big change in speed either way, fails the job.
2. **Web:** installs Emscripten, runs `npm ci` and `npm run build`, which builds the wasm module, type-checks and writes `docs/`. It then runs the same tests compiled to wasm in Node, the site's smoke tests in Chromium, and the image tests' scenes in Chromium and Firefox.
3. **Compare renderings:** compares the scenes as native, Chromium and Firefox drew them, with each other and with the reference renderings (see [Image tests](#image-tests)). The numbers appear on the run's page, with a link to the report with the pictures (the `rendering-comparison.html` artifact, which opens in the browser).
4. **On `main` only, if everything passes:** publishes `docs/` to GitHub Pages, with the rendering comparison at `ci/renderings/`, and replaces the [`latest` release](../../releases/latest) with the new Linux binary. If anything fails, both keep their previous version.

One-time setup: in the repository on GitHub, open **Settings → Pages** and set **Source** to **GitHub Actions**.

## Tests

Tests use [doctest](https://github.com/doctest/doctest) and live next to their module (e.g. `cpp/modules/Core/tests/`). Register a test executable with `viewer_add_test(Name sources...)` from `cmake/testing.cmake`. It is then built in both presets.

```bash
cd cpp
ctest --test-dir build/native --output-on-failure   # native
ctest --test-dir build/web --output-on-failure      # wasm, run in Node (after building the web preset)
```

The wasm run matters: wasm32 has a 32-bit `size_t` and `long`, uses libc++, and has no exception support. A `throw` aborts the program. Node has no GPU, so only GPU-free tests run there.

`GpuDeviceTests` drive a real GPU and are native only: they render offscreen and read the pixels back. CI runs them on Mesa's software Vulkan driver (lavapipe, package `mesa-vulkan-drivers`); without a GPU they fail rather than skip.

The built site has smoke tests in a real browser ([Playwright](https://playwright.dev), Chromium with WebGPU on its software renderer, SwiftShader). They need Node 20 or newer:

```bash
cd web
npm run build                              # writes the site to docs/
npx playwright install chromium firefox    # once
npm run test:e2e
```

### Image tests

Scenes (`Viewer::Scene`, in `cpp/apps/ViewerApp/src/Scene.cpp`) are fixed pictures, drawn alike on every platform: the same data, size (in physical pixels, at a pixel ratio of 1), colors, view and pointer.

| Scene | Shows |
|---|---|
| `hour` | the synthetic trades from 12:00 to 13:00 as markers, one ringed |
| `day` | the whole synthetic day as column summaries, one highlighted |
| `opaque` | a buy and a sell, opaque, in colors chosen for the test, the buy ringed |
| `blended` | the same at half opacity over the background |

Each scene knows the color of some pixels in advance, single ones or whole areas:

- **everywhere:** the margins left for axis labels, which nothing is drawn in, all background;
- **`opaque` and `blended`:** the centers of the trades the scene placed, the ring, the background between them;
- **`hour` and `day`:** found once the scene is set up, from where the app drew things: the time axis's grid lines in the plot's top rows (which the price axis keeps free of trades), the ring around the picked trade, the middle of the highlighted column.

`Scene::show()` returns them. The test scenes' colors are whole 255ths, so flat ones must come out exact; blended ones, and the default theme's colors that fall halfway between two values, may be off by 1. Scenes are drawn:

| Where | How | Checks there |
|---|---|---|
| native, offscreen | `ViewerAppTests` | known pixels |
| native, through a window | `tools/render-native.sh` runs `ViewerApp --scene=<name> --snapshot=<png>` for each | the frame reads back from the window's surface |
| Chromium and Firefox | `web/tests/scenes.spec.ts` opens `scene.html?scene=<name>` | the canvas, read back with `drawImage`, is exactly what the engine drew |

Each platform's renderings go to `renderings/<platform>/` (gitignored): `<scene>.png`, and its known pixels as `<scene>.json`. `tools/compare-renderings.mjs` then compares every pair, and each platform with `tools/reference-renderings/`, drawn natively on lavapipe. It also checks every rendering's known pixels: the only check of the window and browser renderings' known pixels. It writes `renderings/report/rendering-comparison.html`: for each scene, the known pixels as each platform drew them, and a grid of every platform's rendering and each pair's difference, scaled so the largest difference is white, with the numbers. A pair fails if more than 0.05% of its pixels differ visibly (by more than 32/255), or more than 2% beyond rounding (by more than 2/255). Edges fall slightly differently on each GPU, so a few pixels always differ; a missing marker fails.

```bash
(cd tools && npm ci)                            # once: pngjs
VK_ICD_FILENAMES=$(ls /usr/share/vulkan/icd.d/lvp_icd*.json | head -1) \
  tools/render-native.sh                        # natively, on lavapipe; opens a window per scene
(cd web && npx playwright test scenes.spec.ts)  # Chromium and Firefox, after npm run build
node tools/compare-renderings.mjs               # writes renderings/report/
```

After a change meant to alter what's drawn, the references need replacing. Take them from CI rather than your machine, so they match CI's lavapipe exactly: download the run's `renderings-native` artifact (from the run's page, or with the GitHub CLI), then make its native renderings the reference:

```bash
gh run download <run id> --name renderings-native --dir /tmp/ci-renderings
node tools/compare-renderings.mjs --update-reference /tmp/ci-renderings
```

Firefox enables WebGPU (with the `dom.webgpu.enabled` pref) only under Wayland: under X11 or with no display, it reports WebGPU as blocklisted. CI runs it under a headless Weston.

## Choosing the GPU

The web can't list GPUs. It can only send a `powerPreference` hint when it requests an adapter. The page has a GPU selector that recreates the viewer with that hint. The browser may ignore it (on Windows, the OS graphics settings usually decide). What a browser reveals about the WebGPU adapter varies. Some give `vendor` and `architecture` (for example `intel gen-9`). Others give nothing. Few give the exact device. When the browser reveals none of these, the viewer falls back to the renderer string WebGL reports. That is usually more detailed, but it may name a different GPU on multi-GPU machines.

## When things go wrong

| What | What happens | Tested by |
|---|---|---|
| On the web, the GPU device is lost (driver reset, the browser's GPU process crashing) | The app creates a new engine on a new device and gives it everything again: trades, view, size, colors. Meanwhile the page says the GPU is restarting. | A browser test loses the device on purpose, then compares the pixels drawn before and after: they're identical. `ViewerAppTests` does the same offscreen, natively, to test the app's part in C++. |
| In a native window, the GPU device is lost | The app crashes: wgpu-native panics (see below). | Not tested: it's wgpu-native's behavior. |
| WebGPU reports an error nothing caught (a validation error means a bug) | Logged, and the first 16 are kept. The page shows the first one in its header. | Every scene must draw with none. |
| A file has more trades than the GPU's largest buffer holds | The device is requested with the adapter's largest buffer size, often far above WebGPU's default 256 MiB, and 20 bytes per trade. Past that, loading fails with a message, and the trades on show stay. | `ViewerAppTests` caps an app at the synthetic day's trades (`Engine::Params::maxTrades`) and loads one more. `GpuDeviceTests` checks that a GPU buffer refuses to grow past the limit, and stops growing at it. |
| The wasm heap runs out of memory | It can grow to 4 GiB, the most a wasm32 module can address. Past that, the module stops, and the page starts a new one with the synthetic day. It says the data is too large, how much memory the viewer had, and its most. | A browser test asks for 4 GiB at once, which fails without using any. |
| The wasm module stops for another reason (a bug) | The page starts a new module with the synthetic day, and says something went wrong. The reason goes to the console. | A browser test aborts the module. |
| Natively, memory runs out | It says "Out of memory" with the memory in use, without allocating, and aborts: exceptions are off. | Not tested: doctest can't test code that aborts. |

**Losing the device natively.** wgpu-native (v29) notices a lost device only on the next call to it, and some calls then panic instead of failing: submitting work, getting a window's texture for a frame, and presenting it. A real loss, such as a driver reset, surfaces at exactly those calls, so in a native window it crashes the app whatever the app checks. Recovering is for the web: browsers turn every call on a lost device into nothing, and the engine needs no checks there. Offscreen, natively, a loss surfaces at an earlier call, so the app's restart can be tested in C++. That needs one guard, since the frame's submit comes after: everything submits through `Gpu::Context::submit()`, which drops the commands once the device is lost. `Context.hpp` declares `wgpuQueueSubmit` deprecated, so any other call fails to compile, with a message saying to use `submit()`. The engine itself never checks.

**Test hooks.** Tests that lose the GPU create the engine themselves and hand it to the app, keeping a pointer to it. The browser tests need theirs in the published build, which is what they run against, so they're grouped apart from the viewer: `window.viewerTesting` (`loseGpu`, `crash`, `exhaustMemory`, bound as `Testing` in `WebMain.cpp`). Each harms only the page that calls it.

**Memory.** The app counts the memory its large parts hold, room to grow included. Each trade takes 77 bytes: 25 for the trade, 20 for running totals and 32 for the price tree. On the GPU it takes 20. Natively the app logs a breakdown after loading, with the process's resident memory. The page shows the same breakdown in the data panel, under "Memory", with the wasm heap. The derived data (running totals, price tree, column summaries) adds about 208% to the trades. Tests check these numbers exactly, and that 10 rounds of zooming, panning and resizing leave them as they were. Trades are copied to vectors of exactly their size after loading, since reading leaves up to half of their room unused. `shrink_to_fit()` would do nothing here: libstdc++ skips it without exceptions.

## Viewing trades

Each trade is a disc: time across, price up, green for buys and red for sells, and larger for bigger amounts. The view opens on 12:00–13:00 UTC of the first trade's day. The price axis fits the trades in view.

The axes tick at round values: prices in steps of 1, 2 or 5 times a power of ten, and times from 1 µs up to whole days. Labels show as much precision as the step needs, and the date at midnight. `Core::Plot::Axis` works out the ticks for both platforms. The engine draws them as one-pixel grid lines under the trades, in their own pass (`grid`), and the web page writes the labels in margins the plot leaves free. Natively, the labels will come with the ImGui panel; the grid already shows.

| | Web | Native |
|---|---|---|
| Zoom around the pointer | Mouse wheel | Mouse wheel |
| Pan | Drag | Drag |
| 12:00–13:00 | Button | `R` |
| Whole day | Button | `D` |
| Marker size: area ∝ amount, or log of amount | Size menu | `M` |
| Details of the nearest trade, or bar | Point at it: a tooltip | Point at it: the window title |
| Draw every trade, even when crowded | Every trade checkbox | `S` |

Time ranges are half-open: a trade at the end time belongs to the next range.

The toolbar (web) and the window title (native) show how many trades are in view and their total amount. Amounts are added up in whole units of 10⁻⁸ BTC, the smallest step Binance trades in, so totals are exact. Running totals, built once when trades load, give the total of any range in constant time.

### Summaries when zoomed out

A view with more than 32 trades per pixel column, on average, draws a summary of each column instead of its markers. Below that, every trade in view is drawn, as before. With the synthetic day at 1600 pixels across, that's the views longer than about 2 hours: the initial hour (about 13 trades per pixel on the brief's file, 18 synthetic) shows every trade, and the whole day (about 270) shows summaries.

- **What's drawn:** one bar per pixel column, from the lowest to the highest price traded in it. Its color blends from the sell color to the buy color by the buys' share of the amount, and it's fainter the less was traded, relative to the busiest column in view. A column whose trades share one price is still 2 pixels tall.
- **Saying so:** the toolbar shows "Summarized: N bars, ~M trades each", and the legend explains the bars instead of the marker sizes. Pointing at a bar shows its time range, trade count by side, price range and amount by side.
- **Every trade:** the toolbar's Every trade checkbox (`S` natively) draws every trade however crowded the view, which is slow when zoomed out.
- **Threshold:** set from code with `App::setSummaryThreshold`, or `viewer.setSummaryThreshold()` on the web. It isn't in the UI.

Columns hold whole microseconds: column i of n spans [start + i·length / n, start + (i + 1)·length / n), so every trade is in exactly one, and the counts and amounts add up to the view's. Each column is found by binary search, and its price range and amounts come from structures built once when trades load, so a column costs O(log n) whatever it holds:

- **Running totals by side** (`RunningTotals`): amounts in whole 10⁻⁸ BTC units, as for the view's total, plus the buys' amounts and count.
- **A min/max tree** (`PriceTree`): a segment tree of prices, 32 bytes per trade. It also fits the price axis, which read every trade in view before: at the whole day, the view update now takes 0.12 ms instead of about 2 ms (`BenchmarkApp`, release build).

Other kinds of summary (separate buy and sell bars, a density grid, keeping markers in quiet columns) are planned, with a menu to choose between them.

### Cursor and picking

Pointing at the plot picks a trade, rings it, and shows its time (to the microsecond), price, amount and side. While summaries are shown, it picks the nearest bar instead, within the same 24 pixels (`Core::Plot::pickColumn`), and draws it in the cursor color. The rule for trades, in `Core::Plot::pickTrade`:

1. **Nearest center.** The trade whose marker center is closest to the pointer, by straight-line distance on screen, if it is within 24 CSS or window pixels. Distance is measured in pixels because time and price have no common unit, and pixels are what the user sees: a trade a few microseconds away but far up the price axis is far away.
2. **Under the pointer.** Otherwise, a trade whose marker the pointer is on: within its radius of its center. Markers are at most 16 pixels in radius, so with today's sizes rule 1 already finds every such trade; rule 2 matters if markers grow larger than the pick radius.
3. **Ties** go to the later trade, which is drawn on top. Only trades in view count, and nothing is picked from the margins.

Picking runs on the CPU in double precision. Trades are sorted by time, so a binary search finds those within reach horizontally (the larger of the pick radius and the largest marker), and only those are measured: 48 pixels of a 1600-pixel plot, about 13,000 of the synthetic day's 432,544 trades when the whole day is in view. Zooming and panning pick again, so the pick always matches what's under the pointer. The engine draws the ring in the trades pass, with the same placement maths as the markers, in the theme's `--cursor` color.

### Legend

The web toolbar has a legend: the buy and sell colors, and marker sizes for a few amounts on the chosen scale. Sizes stay between 1.5 and 16 pixels, so the legend's first and last sizes stand for every smaller (≤) or larger (≥) amount too. The area scale reaches its limits at 0.0625 and 7.11 BTC, and the log scale at 0.0001 and 100 BTC. Natively, the log shows the same legend at startup and whenever `M` changes the scale.

The sizes are set in one place, `Gpu/Market/Style.hpp`, and the colors in the theme (below). The trades shader gets both as uniforms, and the legend is built from the same values, so the two can't drift apart. A GPU test draws one trade of each legend amount and measures it: its diameter matches the legend to within a pixel, at pixel ratios 1 and 2, and its color matches the legend's color at its opacity.

### Colors

The stylesheet sets the plot's colors, as CSS custom properties in `web/src/index.css`: `--plot-background`, `--plot-grid`, `--buy`, `--sell`, `--cursor` and `--marker-opacity`. The viewer reads them when it starts (`web/src/viewer/theme.ts`) and passes them to the engine (`Engine::setTheme`), so one stylesheet colors the page and the plot together, and a color-blind palette or a light theme is a CSS change. The native app uses the same defaults, from `Gpu::Market::Type::Theme`.

Colors are sRGB values, as CSS gives them, and the engine writes them as they are. Natively, it skips the sRGB surface formats that Vulkan lists first: those would convert the colors a second time and draw them lighter than on the web.

### Frame times

`BenchmarkApp <table.md> [trades.csv.gz]` draws offscreen at 1600 × 900 (Task 3's viewport) and writes, for the whole day drawing every trade, the whole day, 12:00–13:00, a minute and a second: the CPU time to update the view, the CPU phases of a frame (acquire, encode, submit) and each GPU pass (`grid`, then `trades` or `columns`), as the median and 95th percentile of 60 frames. It draws one frame at a time, so each is measured alone. CI runs it on lavapipe, a Vulkan driver on the CPU, so compare its runs with each other rather than with real GPUs.

On an Intel HD 520 with the synthetic day (release build, medians):

| View | Drawn | GPU total | View update (CPU) |
|---|---|--:|--:|
| Whole day, every trade | 432,544 markers | 22.0 ms | 0.11 ms |
| Whole day | 1600 bars | 0.21–0.26 ms | 1.3 ms |
| 12:00–13:00 | 17,900 markers | 0.74–0.82 ms | 0.04–0.05 ms |
| 1 minute | 290 markers | 0.22–0.24 ms | 0.06 ms |

Summaries make the whole day about 100 times cheaper on the GPU. Working them out costs 1.3 ms of CPU per view change, mostly cache misses in the tree; reading the day's trades in order once might be faster at that zoom, which is worth measuring.

Each marker is one equilateral triangle around its disc, the smallest triangle around a circle. Measured with every trade of the day drawn, two runs each:

| Marker shape | Vertices | `trades` pass, whole day |
|---|--:|--:|
| Square, two triangles | 6 | 36.6 ms |
| Square, triangle strip | 4 | 36.6 ms |
| Equilateral triangle | 3 | 21.9 ms |

Fewer vertices alone didn't help (the strip); halving the triangles did. Most markers are a few pixels across, and GPUs pay a fixed cost per triangle. The triangle covers 30% more pixels than the square, which costs nothing measurable at the other zoom levels (hundredths of a millisecond, within noise).

GPU times are in nanoseconds on every platform. wgpu-native counts timestamps in device ticks (83.3 ns each on Intel's Skylake GPUs, for example), so the profiler multiplies by the tick length it reports (`wgpuQueueGetTimestampPeriod`). Browsers report nanoseconds already.

### Memory and speed between commits

CI catches changes in what the viewer costs (`tools/check-benchmark.mjs`). `BenchmarkApp` writes its numbers beside its table, as `benchmark.json`, and CI compares them with the baseline in [`tools/benchmark-baseline.csv`](tools/benchmark-baseline.csv):

| Numbers | Compared with | Fails when |
|---|---|---|
| Memory the synthetic day takes, with the whole day in view: trades, running totals, price tree, column summaries, GPU buffers and textures | The platform's last row, exactly. Memory is the same on every machine (lavapipe and an Intel GPU agree to the byte). | Any change, less too. |
| Times: reading the trades, showing them (derived data and upload), and each view's update, CPU frame and GPU frame (medians of 60 frames) | The platform's last row on the same GPU. | More than 1.5 times slower or faster, and by more than 0.05 ms. |

Failing when things get faster too makes a gain part of the baseline, so losing it later fails. A fixed baseline also catches slow creep, which comparing with recent runs would follow along. A platform or GPU with no row yet fails, so a check never quietly stops checking.

Some numbers are too unsteady to fail a build on, such as a browser's GPU times; the benchmark marks them `flaky`. They're shown on the run's page and kept in the baseline like the rest, marked "recorded only", and never checked.

**The baseline only changes by hand,** so it's also the log of every change in cost: each row has the date, the commit measured, the platform and GPU, a description of what changed and why, and every number. When a change is meant, the failing run's page gives the command that makes its numbers the baseline; add the description and commit the CSV:

```bash
node tools/check-benchmark.mjs accept <run-id> "Shrink the price tree to n entries"
```

It downloads the run's `benchmark` artifact with the [GitHub CLI](https://cli.github.com/) (`gh`), so the times are CI's own: times measured on another machine mean nothing to CI's runner. Without `gh`, download and unzip the artifact from the run's page, and pass its `benchmark.json` instead of the run id. CI's `benchmark.json` names the commit it measured (`BenchmarkApp --commit`). A local run's doesn't, so it counts as the commit checked out, marked `-dirty` with changes on top. A local run is enough for a memory change, which is the same everywhere:

```bash
cpp/build/native-release/apps/BenchmarkApp/BenchmarkApp /tmp/benchmark.md data/binance_trades_2019-12-01_BTCUSDT.csv.gz
node tools/check-benchmark.mjs check /tmp/benchmark.json
node tools/check-benchmark.mjs accept /tmp/benchmark.json "Shrink the price tree to n entries"
```

### GPU buffer layout

Each trade takes 20 bytes in one vertex buffer and is drawn as an instance of a triangle:

| Bytes | Field |
|---|---|
| 0–7 | time, µs since 1970, as two u32 halves |
| 8–11 | price, f32 |
| 12–15 | amount, f32 |
| 16–19 | side, u32 |

A GPU has no 64-bit floats, and a day in microseconds needs 37 bits. The shader subtracts the view's start in 64-bit integer math, then converts the small difference to f32, so positions stay exact to the microsecond at any zoom. The CPU finds the trades in view by binary search, and only those are drawn. The buffer can be appended to: it keeps spare room, and when that runs out it moves to a bigger buffer, copying on the GPU.
